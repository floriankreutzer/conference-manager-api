# Protected invited Customer access

This prepared owned composition is inactive. It installs no HTTP route, provider,
worker, timer, credential or migration and creates no live recipient, identity or
session. Whole protected-root, Microsoft, email-client and browser acceptance remain
open under SaaS1 issue351. Ordinary and closed Demo roots remain unchanged.

`createProtectedInvitedCustomerAccess` constructs canonical email challenge,
admission, audit and protected invited-session components for a fixed environment
and UUID deployment epoch. Neither the browser nor a supplied repository chooses
classification, proof factory or session namespace. Existing eight-digit random
codes, browser/CSRF binding, encryption, admission snapshots, role policy, attempt,
source/recipient budgets and retention bounds are reused.

Every anonymous entry acquires the separate bounded shared deployment lease before
any read or mutation, including unknown recipients which never reach a membership
predicate. The business pool remains available with max1. Capture qualifies each
entry from the existing at-most-100 snapshot before issuing proof or queueing mail;
more than 100 candidates retain the existing neutral fail-closed behavior. Only
captured current REAL memberships enter the snapshot. Later memberships cannot
expand it. Non-REAL-only recipients follow the same neutral response without a
mailbox grant or code delivery.

Choices recheck current REAL custody in one business transaction before projecting
a label. Admission rechecks it before business mutation and takes the Tenant write
lock directly, avoiding shared-to-exclusive upgrade deadlocks between admissions.
The same fixed predicate used by dispatch requires the current deployment epoch,
immutable REAL classification with null synthetic fields, eligible lifecycle,
live shared lease and exact active transaction/client. Canonical member, invitation,
User, role, proof, audit and one-use consumption checks remain mandatory. Qualified
session issuance joins that same admission transaction; failure rolls back the grant.

Email flow-binding and mailbox-code MAC keys are HMAC-derived from independent
external secrets with fixed purpose, environment and protected UUID epoch. An old
unverified or verified pending browser flow cannot cross a cutover into the new
session namespace. Persistent cipher/recipient lookup, audit and source-budget
keys are never epoch-derived: retained encrypted custody and abuse evidence survive.
This derivation supplies no default secret and cannot authorize a Tenant or session.
No promise of erasing JavaScript strings is made.

The generic repositories retain an optional server-only qualification port for
ordinary compatibility; only the owned factory fixes that port and the enclosing
lease. It is not an activation API. The optional server-owned Microsoft
client additionally composes [qualified primary/link flows](PROTECTED-INVITED-MICROSOFT.md).
Full runtime composition must still handle the combined real/delegated session
resolver, explicit account switching, invitation/configuration mode guards and
outbound operating acceptance. This component does not independently resolve those responsibilities.

Focused progression/negative tests cover epoch/purpose/environment separation,
strict qualification, mixed snapshots, absent mail/proof for denied entries,
label suppression, max1 transaction ownership, mutation-free denial and direct
write locks. Native coverage additionally requires exact-source PostgreSQL CI:
actual encrypted outbox readback without outbound delivery, REAL/unclassified/
synthetic candidates, late membership exclusion, concurrent one-use admission,
protected session and audit readback, pending and verified flow cutover denial,
unchanged source/recipient budgets and preserved real identities/history. Software
fixtures are not live Microsoft, physical passkey or mail-client acceptance.
