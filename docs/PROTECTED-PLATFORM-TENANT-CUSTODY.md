# Protected Platform target custody

SaaS1 issue351. Prepared component; no deployment, profile or flag activation.
Existing ordinary and closed Demo persistence constructors retain their default
behavior. No schema or frozen migration bytes change.

## Visibility and target policy

The optional fixed server-side `protectedRuntime` contains exactly environment
and the non-reusable deployment UUID. The persistence factory validates it before
creating a pool, then owns immutable scope copies for all target adapters. A
malformed explicit profile fails; it cannot silently select the ordinary path.
The owned protected Platform authentication factory supplies the same profile to
its audit target policy. Browser requests cannot select this configuration.

Protected results contain only registered Tenants in the current deployment.
Canonical all/allowlist rights continue to determine REAL visibility. The actual
operator's own active synthetic generation is an explicit additional target set,
including for an allowlisted operator who created that generation through the
separate exact-proof generation service. No role or operation permission is
added. Normal authentication, current Actor/version, actual source session,
normal MFA, actual keys and fresh exact request proof remain with their existing
owners. An all-Tenant scope or an explicit legacy allowlist entry cannot expose a
foreign synthetic generation. PROD cannot expose synthetic targets. Unclassified,
archived or captured-stale synthetic custody is not an active target.

The pure persistence SQL contract returns only bounded fixed predicates and bound
values, not an executor, pool, identity, session, issuer, mutation or grant. It
checks immutable registry classification, deployment UUID, current owner/provider
and version, generation state and eligible Tenant lifecycle. It intersects REAL
canonical rights and separately checks own synthetic custody. Ordinary callers
with no protected profile do not execute private-registry SQL. Closed Demo role
privileges remain unchanged; no protected runtime/reset authority enters Demo.

Directory, readiness and Microsoft-health pages apply custody before pagination.
Their signed cursor filters additionally bind environment/UUID, so a cursor from
another profile cannot continue a page. Direct target policy and diagnostic
reads use the same custody. Lifecycle, entitlement and recovery mutation SQL
revalidates it inside the actual mutation transaction. Creation retains canonical
all-scope authority and additionally requires the current deployment; the owned
REAL onboarding service remains responsible for atomic classification and owner-
inclusive invitations. No generic creation path is activated by this component.

## Execution and retained data

The future owned root must retain the accepted whole-request shared lease before
session resolution through business/audit/response, and use the corresponding
exclusive generation/reset protocol. The SQL guard is not a replacement for that
reset barrier, exact proof or business transaction. Worker/provider leases and
owned runtime composition remain separately required.

Reset archives previous Tenants through canonical services and creates fresh
ones. Visibility changes without deleting retained Rooms, Requests, identities,
keys, memberships, Platform records or audit history. Current-target denial does
not imply removal of retained historical evidence. No TRUNCATE, broad deletion,
identity remapping or external call is introduced.

invitation cases pass. Lint and module-boundary checks pass. A new native max1

The low-level target authorization probe is not an independent privileged grant.
