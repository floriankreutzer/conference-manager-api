# Owned protected Platform process

`npm run start:protected:platform` is an explicit additional entrypoint. It does
not activate a deployment or alter ordinary conditional-access/closed Demo
behavior. DEV/INT/PROD retain production security constraints and independent
database UUID/integer Platform epoch/client/origin namespaces. Only start/stop
is exposed; no configurable identity, issuer, verifier, repository, driver,
provider, fallback or request-handler implementation enters the owned process.

The root owns configuration, verified-TLS separate business/lease pools,
current schema/UUID/minimal role readiness, the existing pinned primary and
WebAuthn factories, current operator-owned target custody and the actual
canonical operational services. Startup/shutdown is serialized and resource
errors are redacted. The exact new Operations composition/entrypoint ownership
is classified in both architecture gates; Customer roots, lower layers and
closed Demo graphs remain forbidden. No broad boundary exception is added.

The explicit `passkey_setup` profile exposes only authentication/health/session
routes and starts no business projection worker. Its session resolver grants no
business login. `application_passkey` requires at least two actual current
credentials and publishes only normal MFA cookies after exact-operation proofs;
no reusable elevated cookie or conditional-access fallback is exposed. Initial
primary/keys/recovery still require the existing real Microsoft and offline
TID/OID-approved operating ceremonies. None attestation is not proof of distinct
physical devices.

The active business route family composes the owner-inclusive multi-recipient
onboarding and invitation administration services with protected REAL
classification in the same proof transaction. The configured owner contact is
explicit; no address or authority is inferred from provider claims. Canonical
request/CSRF/permission/target/idempotency/audit controls still execute beneath
the fresh exact-request proof wrapper. The complete HTTP handler is under the
shared current deployment lease after bounded transport validation. Only the
two existing exact synthetic proof-completion paths enter their own separately
stamped exclusive transactions without a surrounding shared lease.

Opted-in DEV/INT synthetic routes use the owned exclusive proof service, own-only
generation directory/replacement, signed browser binding and intent-cookie
handoff. Missing opt-in composes none of these routes; PROD refuses opt-in.
No browser-supplied operator, Tenant mode or provider fallback becomes authority.
Generation/reset retains canonical identities, keys, audit and archived business
history. Durable SIM/calendar final-write authority, discovery/media/business UI
and full browser/operating acceptance remain separate required work.

The active projection worker uses the existing periodic durable consume/rebuild
interface under the current shared readiness scope. Its optional persistent
LISTEN port is omitted from this bounded business pool so a max1 configuration
has a free business connection. Setup disables the worker through a closed
construction-only boolean; ordinary composition defaults remain enabled.
Platform metrics use the canonical Platform route vocabulary. Health/readiness
does not prove every business feature or an external deployment is accepted.

The positive grant manifest additionally exposes only mailbox/purpose delivery
metadata required by the canonical invitation-audit trigger, plus Customer
session issued_at for canonical revocation timestamps. Delivery ciphertext,
Customer session issuance, offline enrollment-grant INSERT and private marker/
maintenance execution stay denied. No schema or actual role installation is
performed by process construction/startup.

Seven focused cases cover three environments, setup/opt-in construction, closed
ports, refused configuration, unavailable actual loopback database/concurrent
stop and ownership isolation. The new native case is prepared for exact-source
execution, not yet accepted: both actual child processes use the existing
ephemeral TLS/SCRAM PostgreSQL fixture, real restricted password connections and
max1 business/lease pools. A setup process must start while its fixture role
lacks a business source read, proving that no projection runs. Canonical fixture
provisioning creates one Microsoft-shaped operator and two actual software P256
keys outside the roots; neither primary/verifier/session implementation is
injected into a root.

The native test then exercises fresh exact-assertion REAL creation with owner
and participant invitations, replay denial, current normal MFA, three-customer
generation, actual cross-origin HTTP handoff through both owned processes,
current Customer delegation, REAL-only Microsoft refusal, actual cooldown and
fresh-assertion reset, old-session denial, preserved archived rooms/requests,
retained REAL invitations/classification, audit, redacted logs and shutdown.
The Customer native fixture's original assertions remain intact; process/HTTP
plumbing is shared and its pools tighten to max1. These are HTTP/software-key
fixtures, not browser SameSite/document/RP, live Microsoft, physical-key recovery,
real email delivery or deployed artifact-pair/cutover acceptance. All unchanged
permanent four-pair full Demo progression/two-reset gates and fresh actual-main
all9 contexts remain mandatory. SaaS1 issue351/milestone2 remains open.
