# Owned protected synthetic calendar runtime

This candidate composes the durable synthetic calendar in the closed protected
Customer process and prepares its resources in the closed Platform generation
transaction. It requires the existing explicit DEV/INT synthetic profile. PROD
cannot select this branch. No provider, issuer, clock or persistence override is
exposed by either root. The immutable current registry selects REAL or synthetic;
REAL retains its Microsoft calendar provider and current invited membership.

## Generation and final authority

The owned Platform root enables technical calendar preparation explicitly in its
private generation repository. The component default remains disabled. Each new
generation receives truthful `synthetic_calendar` active Integrations and one
private resource per actual active Room, after business seeding and before the
same transaction activates the generation. A zero-room onboarding Tenant has no
resources. This creates no Microsoft identity binding, consent or connection.
Reset preserves archived resources, events, business records, identities and audit.

The Customer root owns both fixed provider factories and a private final-authority
guard. The shared persistence module accepts only a construction-time factory;
it does not import protected identity through the Demo dependency graph. Default
legacy/Demo composition keeps the existing Microsoft guard. Root readiness now
retains every base persistence check in addition to exact schema/role/UUID checks
and, when enabled, the narrow calendar-source function permission.

Every protected final confirmation requalifies the actual server principal and
current registry/deployment/Tenant under the exact live shared execution scope
and active business transaction. REAL locks its current User/session, rechecks
membership and delegates the unchanged Microsoft authority SQL. Synthetic checks
the complete canonical signed handoff/source evidence before and after the
narrow SQL063 source-lock routine locks current operator/source/User/session.
The routine does not authenticate or grant booking authority by itself. Missing,
revoked, expired, foreign, unavailable or changed custody denies the final write.

Synthetic final authority also locks current active Integration/Room, requires
exact generation-owned connection/resource values and, with calendar writes on,
the actual active private event plus persisted booking reference with the same
request, room, integration, period and idempotency key. With writes off, an active
event prevents confirmation; existing reference cleanup rules still apply. No
Customer resource UPDATE or Platform source UPDATE permission is added. Other
request transitions and booking-change approval also fence current Customer
custody in their final transaction. Existing policy, entitlement, version,
conflict, audit, compensation and booking-reference logic remain authoritative.
