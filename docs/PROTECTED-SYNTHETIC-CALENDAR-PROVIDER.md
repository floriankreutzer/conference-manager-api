# Durable protected synthetic calendar provider

This prepared adapter connects the existing calendar contract to private063
PostgreSQL state. It has no network, Microsoft, mail, Demo, credential, clock or
fallback port. It is not yet activated in an owned process. Generation resource
preparation, final booking authority, discovery/import, honest capabilities/UI,
media and full browser/operating acceptance remain separate SaaS1 issue351 work.

## Binding and operations

The closed factory accepts only its exact five-method private repository. It
captures own function values at construction. Selection accepts only internal
Tenant/Room or exact persisted Integration/connection/resource references. The
repository owns DEV/INT and the UUID epoch. Each operation requires an enclosing
live exact shared execution scope and freshly checks resource, immutable registry,
current generation/deployment, current active owner/security version, active
Tenant/Room and the actual truthful synthetic Integration before data access.
There is no REAL fallback or browser-controlled runtime/provider selection.

Returned metadata declares `synthetic_calendar` and `platform_delegation`. Each
method captures its immutable binding, validates closed own-value input, bounded
finite canonical UTC periods, internal request/correlation IDs, reservation phase
and exact resource/reference ownership. Domain values are pure; provider errors
are translated at the adapter/persistence boundaries. Existing common calendar
exports retain their API/semantics and re-export the extracted domain room-ID,
phase and idempotency validators. No architecture gate was weakened or exception
added when an initial integration-contract dependency failed the boundary check.

Availability excludes the current Request and reports a bounded conflict
indicator. Validation uses that same result. Creation stores an actual event and
its idempotency key; a namespaced deterministic UUIDv8 lets simultaneous same-key
retries address the same row before uniqueness is checked. Exact same-request/
period retries return existing. Reuse with changed data or a cancelled event
fails duplicate rather than resurrecting or creating another event. Updates
retain ownership and return unchanged only for the current exact period.
Cancellation is terminal, repeatable and preserves the original period. Different
Requests cannot cancel/update the same event through a supplied reference.

SQL063 resource revisions serialize simultaneous reservations; conflicts,
serialization, authorization and bounded timeout failures become fixed calendar
error kinds without SQL, credentials or provider detail. There is no implicit
retry. The canonical application still owns role/entitlement/workflow checks,
local conflicts, booking reference attempt numbers, audit, compensation and the
final authoritative business transaction. These ports do not issue sessions or
confirm a booking by themselves. Room replacement remains with the existing
create/cancel booking saga; period updates alone are exercised here.
