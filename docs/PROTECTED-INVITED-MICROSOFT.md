# Protected invited Microsoft access

The inactive invited-access composition optionally receives the server-owned fresh
Microsoft client and an independent external protocol secret. With no client,
Microsoft remains uncomposed. This installs no HTTP route or runtime flag and
changes no app registration, callback, secret, consent, default assurance or live
deployment. Canonical primary, protocol and admission contracts remain in
CUSTOMER-MICROSOFT-PRIMARY.md, CUSTOMER-MICROSOFT-FLOWS.md and
CUSTOMER-MICROSOFT-HTTP.md. Full protected-root operating acceptance remains open.

The same owned audit and protected invited-session components serve email and
Microsoft. All authentication/admission/account entries acquire the current
separate deployment lease. Source fingerprints use the unchanged independent
stable source key; protocol/browser/nonce/PKCE/confirmation MAC custody derives
from the external Microsoft-flow secret plus purpose, environment and UUID epoch.
A pending or verified old flow cannot grant a new-epoch session. Persistent lookup,
cipher, audit and source/global abuse counters are not reset at cutover.

Login captures only existing accepted memberships with the exact organizational
Microsoft directory/subject binding, current User/security version, eligible
Tenant and current immutable REAL classification. It never accepts an invitation
through an email claim or creates a User. The existing bounded capture and snapshot
limits remain. REAL qualifications acquire ordered Tenant locks before the
protocol row lock; the protocol browser/status/freshness is checked again under
that lock. Later memberships cannot expand a captured proof. Choices recheck REAL
before projecting labels; selection takes the direct Tenant write lock before
any admission mutation and retains canonical one-use session/audit atomicity.

A link requires an actual fresh email membership/session and new Microsoft primary
proof, followed by explicit browser-bound CSRF confirmation. REAL custody is checked
before email Tenant locks and mutation. Protected callback reservation checks and
locks the email Tenant before its protocol row, then rechecks both, preventing a
Tenant/protocol inversion against confirmation. Read-only account/confirmation
views use one business transaction; max1 never allocates a second connection.
Security-version invalidation, immutable retained link evidence, conflict rejection,
current stored roles and the minimized identity-link audit remain canonical.
No external directory is reinterpreted as a Tenant Microsoft365 connection.

The pinned MSAL code-redemption flow relies on the fixed TLS token endpoint and
adapter claim/protocol checks. It does not independently verify the returned JWT
signature. Software SDK fixtures prove the exercised adapter/custody behavior;
they do not establish live Microsoft, physical authenticator or provider-signature
acceptance. No new claim about independent JWT verification is made here.

Focused progression/negative tests cover pre-lock REAL capture, hidden invalid
labels, mutation-free denied selection, max1 reads, strict qualification of email
principals before link allocation, epoch-separated nonce/PKCE/browser/confirmation,
stale-deployment exclusion before provider/business work, and stable source keys.
Native exact-source CI must additionally exercise actual existing email admission,
explicit software-SDK primary/link custody in isolated REAL/unclassified/synthetic
fixtures, protected REAL session/audit/version readback, denied-mode existing
bindings, one-winner selection and old pending/verified flow cutover rejection.
No live recipient or outbound email is used. Ordinary and permanent Demo regression
checks, all required security contexts and four paired browser/reset gates remain
mandatory; this component alone is not full protected runtime acceptance.
