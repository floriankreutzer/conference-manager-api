# Audit and Security Event Contract

## Authority and scope

Root `AGENTS.md` is authoritative. This document defines the SaaS 0 tenant-scoped audit/security-event boundary introduced by issue #52.

Audit records are not operational logs. Operational logs remain metadata-only diagnostics. Audit records are durable security/business evidence generated by trusted server code.

## Trust model

The browser never supplies authoritative audit tenant, actor, timestamp, outcome, previous/new state, or integrity values.

Tenant-scoped events derive:

- internal Tenant ID from the authenticated server Principal/Tenant context;
- actor User ID from the authenticated Principal, or a validated server-side identity flow where no authenticated Principal exists yet;
- UTC occurrence time from server time;
- correlation ID from the server request/runtime context;
- action/outcome from fixed server-side event taxonomy;
- target and previous/new state from server-side business state;
- integrity metadata only from the persistence adapter.

Platform/operator audit is a separate authorization domain and is not exposed through the tenant endpoint implemented here.

## Event model

Every event contains:

- Tenant ID;
- optional internal actor User ID;
- fixed action;
- target type and target ID;
- optional bounded previous/new state;
- UTC occurrence timestamp;
- correlation/request ID;
- outcome (`success`, `failure`, or `denied`);
- bounded non-secret metadata;
- retention class (`security`, `business`, or `administrative`).

The public tenant API deliberately omits `tenantId`, `previousHash`, `eventHash`, and `integrityVersion` from browser responses. Tenant scope is already established server-side, while integrity fields are verification material rather than presentation data.

## Data minimization

Audit state/metadata is restricted to small flat primitive objects. Nested objects/arrays are rejected.

Keys containing credential-sensitive concepts are rejected, including password, secret, token, cookie, CSRF, authorization, credential, private-key, and session-ID variants. Provider tokens, opaque session credentials, CSRF values, connection strings, raw provider payloads, and secrets must never enter an audit event.

Session events identify the internal User as target and use only role/permission counts or non-secret state labels. Raw session ID/token/hash and provider subject values are intentionally excluded.

## Append-only and tamper evidence

Migration 004 makes `audit_events` append-only through a database trigger that rejects `UPDATE` and `DELETE`.

Events are additionally chained per internal Tenant:

1. append obtains a transaction-scoped advisory lock for that Tenant;
2. the previous event hash is loaded;
3. a canonical event payload plus the previous hash is signed with HMAC-SHA-256;
4. the new event stores `previous_hash`, `event_hash`, and integrity version 1;
5. read access verifies the complete Tenant chain before returning events.

Canonical JSON recursively sorts object keys so PostgreSQL `jsonb` normalization cannot create false integrity failures.

Any runtime using PostgreSQL persistence must provide a stable `AUDIT_HMAC_SECRET` of at least 32 bytes. Pilot/Production require it from external secret management. The secret is never stored in PostgreSQL or source control and must remain stable across application restarts while existing events depend on that key.

`AUDIT_HMAC_SECRET` rotation is not an ordinary deployment configuration change. A rotation requires a reviewed integrity migration/checkpoint strategy that preserves the ability to verify events signed with the previous key. Automatic multi-key verification/rotation is not implemented by #52.

The chain detects record modification/reordering when the HMAC key is not compromised. It does not by itself prove completeness against a privileged actor who can remove an entire suffix or restore an older database snapshot. External anchoring/WORM export and independently controlled retention are production-hardening topics for the later secure-configuration/operations work and must not be claimed as implemented here.

## Atomic business/security mutations

Successful Request transitions and session issue/revoke/rotation append their corresponding success audit event in the same PostgreSQL transaction as the authoritative mutation. If the audit append fails, the business/security mutation rolls back.

Failures that produce no authoritative mutation are appended as separate failure/denial events when a valid Tenant/actor context exists. Events for identities that cannot be mapped to a valid internal Tenant belong to a future platform/security telemetry boundary rather than being forced into another Tenant's audit trail.

Anonymous or otherwise unmapped authentication failures therefore are not assigned to a tenant audit chain. The future identity-provider adapter may emit `authentication.failed` only after it has a trusted internal Tenant/actor mapping or may route unmapped security telemetry to the separate platform security domain.

## Tenant read API

`GET /api/v1/audit` is read-only and requires:

- a valid server-side session;
- a known Tenant context derived from the Principal;
- recognized Tenant authorization snapshot;
- Tenant Admin role;
- explicit `tenant:audit:read` permission.

Pagination uses bounded `limit` (1-100) and an opaque numeric `beforeId` cursor. Unknown or duplicated query fields are rejected.

Every successful audit read appends an `audit.read` event. Denied authorized-context probes append `authorization.denied`. The endpoint never accepts a Tenant selector.

## Retention hooks

Retention classes are recorded now so future lifecycle/export policies can distinguish security, business, and administrative evidence. #52 does not implement physical deletion because the current table is intentionally append-only. Retention execution therefore requires a separately reviewed archive/WORM/export-and-purge design that preserves evidentiary integrity.

## Covered event taxonomy

The current taxonomy reserves server-controlled actions for:

- session issuance/revocation/rotation;
- authentication failure where a valid Tenant scope is available;
- authorization denial;
- Request transition success/failure;
- Tenant configuration and User-permission changes;
- integration connect/disconnect/admin-consent changes;
- calendar operations;
- tenant audit reads.

#52 actively emits events for supported session lifecycle operations, Request workflow outcomes/denials and tenant audit reads. Tenant/User-permission, integration, calendar and provider-authentication actions are reserved for their owning future services; reserving an action name does not claim that workflow is already implemented.
