# Audit and Security Event Contract

## Authority and scope

Root `AGENTS.md` is authoritative. This document defines the Tenant-scoped audit and security-event boundary introduced by SaaS 0 issue #52 and extended by later Tenant lifecycle services.

Audit records are not operational logs. Operational logs remain metadata-only diagnostics. Audit records are durable security and business evidence generated by trusted server code.

## Trust model

The browser never supplies authoritative audit Tenant, actor, timestamp, outcome, previous/new state or integrity values.

Tenant-scoped events derive:

- internal Tenant ID from the authenticated server Principal and Tenant context;
- actor User ID from the authenticated Principal, or a validated server-side identity flow where no authenticated Principal exists yet;
- UTC occurrence time from server time;
- correlation ID from the server request or runtime context;
- action and outcome from the fixed server-side event taxonomy;
- target and previous/new state from server-side business state;
- integrity metadata only from the persistence adapter.

Platform/operator audit is a separate authorization domain and is not exposed through the Tenant endpoint implemented here.

## Event model

Every event contains:

- Tenant ID;
- optional internal actor User ID;
- fixed action;
- target type and target ID;
- optional bounded previous/new state;
- UTC occurrence timestamp;
- correlation/request ID;
- outcome (`success`, `failure` or `denied`);
- bounded non-secret metadata;
- retention class (`security`, `business` or `administrative`).

The public Tenant API deliberately omits `tenantId`, `previousHash`, `eventHash` and `integrityVersion` from browser responses. Tenant scope is already established server-side, while integrity fields are verification material rather than presentation data.

## Data minimization

Audit state and metadata are restricted to small flat primitive objects. Nested objects and arrays are rejected.

Keys containing credential-sensitive concepts are rejected, including password, secret, token, cookie, CSRF, authorization, credential, private-key and session-ID variants. Provider tokens, opaque session credentials, CSRF values, OIDC or consent state, connection strings, raw provider payloads and secrets must never enter an audit event.

Session events identify the internal User as target and use only role/permission counts or non-secret state labels. Raw session ID, token, hash and provider subject values are intentionally excluded.

Microsoft 365 lifecycle events contain only bounded operation, status and reason codes. They exclude internal or provider Tenant IDs, provider User IDs, raw consent state, credentials, access tokens, provider response bodies and provider error descriptions.

## Append-only and tamper evidence

Migration 004 makes `audit_events` append-only through a database trigger that rejects `UPDATE` and `DELETE`.

Events are additionally chained per internal Tenant:

1. append obtains a transaction-scoped advisory lock for that Tenant;
2. the previous event hash is loaded;
3. a canonical event payload plus the previous hash is signed with HMAC-SHA-256;
4. the new event stores `previous_hash`, `event_hash` and integrity version 1;
5. read access verifies the complete Tenant chain before returning events.

Canonical JSON recursively sorts object keys so PostgreSQL `jsonb` normalization cannot create false integrity failures.

Any runtime using PostgreSQL persistence must provide a stable `AUDIT_HMAC_SECRET` of at least 32 bytes. Pilot and Production require it from external secret management. The secret is never stored in PostgreSQL or source control and must remain stable across application restarts while existing events depend on that key.

`AUDIT_HMAC_SECRET` rotation is not an ordinary deployment configuration change. A rotation requires a reviewed integrity migration or checkpoint strategy that preserves the ability to verify events signed with the previous key. Automatic multi-key verification and rotation are not implemented.

The chain detects record modification and reordering when the HMAC key is not compromised. It does not by itself prove completeness against a privileged actor who can remove an entire suffix or restore an older database snapshot. External anchoring, WORM export and independently controlled retention remain production-hardening decisions and must not be claimed as implemented here.

## Atomic business and security mutations

Successful Request transitions, session issue/revoke/rotation, entitlement changes, Tenant onboarding and identity-claim changes, JIT User provisioning, Tenant role changes and Microsoft 365 connection lifecycle changes append their corresponding success audit evidence in the same PostgreSQL transaction as the authoritative mutation. If the audit append fails, the mutation rolls back.

For Microsoft 365, the atomic boundary covers consent-state persistence, connection-state/version changes and local disconnect. External Microsoft consent or Graph calls cannot participate in the PostgreSQL transaction and are never described as transactionally atomic with local state.

Failures that produce no authoritative mutation are appended as separate failure or denial events when a valid Tenant and actor context exists. Events for identities that cannot be mapped to a valid internal Tenant belong to the platform/security telemetry boundary rather than being forced into another Tenant's audit trail.

Anonymous or otherwise unmapped authentication failures therefore are not assigned to a Tenant audit chain. The identity-provider adapter may emit `authentication.failed` only after it has a trusted internal Tenant and actor mapping, or it may route unmapped security telemetry to the separate platform security domain.

## Tenant read API

`GET /api/v1/audit` is read-only and requires:

- a valid server-side session;
- a known Tenant context derived from the Principal;
- recognized Tenant authorization snapshot;
- Tenant Admin role;
- explicit `tenant:audit:read` permission.

Pagination uses bounded `limit` (1-100) and an opaque numeric `beforeId` cursor. Unknown or duplicated query fields are rejected.

Every successful audit read appends an `audit.read` event. Denied authorized-context probes append `authorization.denied`. The endpoint never accepts a Tenant selector.

## Retention hooks

Retention classes are recorded so future lifecycle and export policies can distinguish security, business and administrative evidence. Physical deletion is not implemented because the current table is intentionally append-only. Retention execution requires a separately reviewed archive, WORM or export-and-purge design that preserves evidentiary integrity.

## Covered event taxonomy

The fixed server-controlled taxonomy covers:

- `session.issued`, `session.revoked` and `session.rotated`;
- `authentication.failed` where a valid Tenant scope is available;
- `authorization.denied`;
- `request.transition` and `request.transition_failed`;
- `tenant.configuration.changed` and `tenant.user_permissions.changed`;
- `tenant.entitlement.changed`;
- `tenant.onboarding.invited`, `tenant.identity.claimed` and `tenant.identity.unbound`;
- `tenant.user.provisioned` and `tenant.user.profile_updated`;
- `integration.admin_consent.changed`, `integration.connected`, `integration.verified` and `integration.disconnected`;
- `calendar.operation`;
- `audit.read`.

The corresponding owning services emit only the actions they implement. Reserving a taxonomy value does not by itself claim that a future workflow is complete.

Microsoft 365 connection verification emits `integration.verified` with bounded status evidence. Migration 011 extends the PostgreSQL action constraint for this action and its rollback refuses to remove schema support while verification evidence remains. Connection and audit mutations commit atomically; raw Microsoft identifiers and payloads remain excluded.

Provider-neutral calendar write success metadata is limited to operation, provisional/final phase and disposition. Failure metadata contains only stable provider error classification and retryability. Provider references, raw provider errors, payloads and credentials are excluded.

## Required evidence

Changes to the audit contract require, as applicable:

- event normalization and forbidden-field negative tests;
- Tenant-scoped append/list tests;
- append-only and HMAC-chain integrity tests;
- cross-Tenant isolation tests;
- mutation rollback when audit append fails;
- exact database action-constraint migration and rollback tests;
- concurrency tests for audit-atomic lifecycle changes;
- public-response, log and metric redaction tests;
- rollback guards for durable audit evidence.
